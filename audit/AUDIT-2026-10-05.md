# Audit de GitToSkill — 5 octobre 2026

> Ce rapport décrit l'état initial. Les correctifs appliqués et leurs vérifications sont présentés dans [IMPLEMENTATION-2026-10-05.md](IMPLEMENTATION-2026-10-05.md).

## Diagnostic

Le projet dispose d'une base moderne : Next.js App Router, React 19, Tailwind 4 et TypeScript strict. Une réécriture complète ne se justifie pas. La dette principale concerne la fiabilité du produit, les correctifs de sécurité, le coût des générations répétées et la qualité des preuves utilisées pour produire les skills.

La priorité est de remettre en état le parcours « générer puis installer », de mettre Next.js à jour et de maîtriser les appels GitHub/Azure. Optimiser quelques rendus React aurait un effet secondaire face à ces problèmes.

## 1. Dépendances : correction urgente de Next.js

`pnpm audit` remonte **76 entrées d'avis**, correspondant à **64 identifiants GHSA distincts** sur 15 paquets. Plusieurs avis sont comptés pour différentes versions d'un même paquet ; ce nombre ne représente pas 76 failles distinctes exploitables dans cette application.

| Périmètre du scan | Critiques | Élevées | Modérées | Faibles |
| --- | ---: | ---: | ---: | ---: |
| Toutes les dépendances | 2 | 45 | 25 | 4 |
| Dépendances de production uniquement | 2 | 21 | 16 | 4 |

La classification « production » du gestionnaire inclut aussi des outils de compilation déclarés dans `dependencies`. Elle ne prouve pas leur exposition à une requête HTTP.

Les deux avis critiques portent sur Next.js 16.1.6 :

- **GHSA-p293-qw3h-jr36** : exécution de code à distance sur des serveurs utilisant un système de fichiers Windows. Le projet utilise App Router et n'active pas Cache Components, ce qui correspond au contexte décrit par l'avis. L'hébergement réel reste à vérifier ; développer sous Windows ne signifie pas que le déploiement Vercel utilise Windows. Correction publiée en 16.3.3. [Avis officiel de Vercel](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36).
- **GHSA-2xp9-vwfh-vxw4** : exécution de code à distance lors de l'optimisation d'images AVIF, via une bibliothèque utilisée par `sharp`. Aucune utilisation de `next/image` n'a été trouvée dans le code applicatif, mais l'exposition de l'endpoint d'optimisation doit être vérifiée sur le déploiement. Correction publiée en 16.3.3. [Avis officiel de Vercel](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4).

**Action : passer à Next.js 16.3.8 et `eslint-config-next` 16.3.8**, versions stables retournées par le registre interrogé pendant cet audit. Une mise à jour vers 16.1.7 seulement ne couvre pas les avis critiques cités. Refaire ensuite le scan : la mise à jour de Next.js ne garantit pas la disparition de toutes les alertes transitives.

## 2. Défauts fonctionnels prioritaires

### F01 — Les skills générés peuvent être rejetés à l'installation — P1

**Emplacement :** `lib/generate-skill.ts:97` et `app/api/generate-skill/route.ts:21`.

`buildSkillMarkdown` retourne directement le texte du modèle. Aucun frontmatter YAML `name`/`description` n'est ajouté. Le prompt demande un texte descriptif commençant directement par les sections, sans imposer ces métadonnées.

La spécification Agent Skills exige ces deux champs. La bibliothèque `skills` installée les vérifie également avant de reconnaître le fichier. Une fixture respectant les sections du prompt est rejetée ; la même fixture avec frontmatter est reconnue. [Spécification officielle](https://agentskills.io/specification).

**Correction :** construire les métadonnées côté serveur, avec un nom identique au dossier, une description précise du déclenchement et un YAML correctement échappé. Valider le document avant sa publication ou son installation. Conserver la description de style pour l'interface, mais ajouter au bundle les instructions d'application et les liens vers les références utiles.

**Critère de réussite :** un bundle produit par la génération est découvert puis installé par `skills`, sans dépendre du bon vouloir du modèle pour fournir le format.

### F02 — Fonction inexistante après l'installation — P1

**Emplacement :** `bin/gittoskill.mjs:214`.

`ensureInstalledSkillIgnored` appelle `readTextIfExists`, qui n'est ni définie ni importée. Quand un dépôt Git et un dossier de skill correspondant existent, le CLI peut terminer en erreur après avoir déjà installé le skill. Le défaut est reproduit dans un environnement simulé : `readTextIfExists is not defined`.

**Correction :** implémenter la lecture, traiter explicitement le fichier absent et tester le parcours dans un dépôt temporaire. Les contrôles TypeScript actuels ne couvrent pas ce `.mjs` : `allowJs` seul ne suffit pas à le vérifier.

### F03 — Écritures de références hors du dossier cible possibles — P1

**Emplacement :** `bin/gittoskill.mjs:183`.

Le CLI joint directement `reference.path` reçu de l'API au dossier cible. Une référence `../escaped.md` sort de ce dossier. La reproduction intercepte les écritures : aucun fichier externe n'a été écrasé.

L'API actuelle construit elle-même les chemins depuis les noms GitHub. Ce défaut n'est donc pas démontré comme une exploitation distante à partir d'un simple profil. Il devient dangereux si le backend ou une API personnalisée renvoie un bundle malveillant ou corrompu.

**Correction :** refuser les chemins absolus, lettres de lecteur, séparateurs Windows ambigus, traversées et cibles en dehors de `references/`. Résoudre les chemins puis vérifier leur confinement ; valider aussi le nombre et la taille des fichiers, les doublons et l'identité du bundle. Ne jamais permettre à une référence de remplacer `SKILL.md`.

### F04 — JSON `null` provoque une erreur 500 — P2

**Emplacement :** `app/api/generate-skill/route.ts:71`.

`request.json()` accepte `null`, puis `body.profile` lève une exception avant le bloc qui traite les erreurs de génération. Confirmé en HTTP : statut 500 avec corps vide, au lieu d'un 400 JSON exploitable par l'interface.

**Correction :** traiter le corps comme `unknown`, vérifier qu'il s'agit d'un objet non nul, valider `profile` et imposer des tailles maximales. Une validation manuelle suffit pour ce petit schéma ; un validateur partagé devient utile si le contrat grandit.

### F05 — Résultats tronqués acceptés comme complets — P2

**Emplacement :** `lib/azure-openai.ts:190` et `app/api/generate-skill/route.ts:102`.

Le client ignore `finish_reason` et `usage`. Une réponse contenant du texte avec `finish_reason: "length"` est acceptée. La limite de 2 000 tokens couvre aussi le raisonnement, ce qui peut laisser moins de place au texte visible. [Documentation Microsoft](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/reasoning).

**Correction :** vérifier la fin de génération, détecter les refus/filtres et valider les sections et leurs sources. Mesurer les tokens réels avant de régler le budget. Tester un effort de raisonnement plus faible sur un corpus de profils ; augmenter systématiquement le budget ou choisir le modèle le plus récent ne garantit pas un meilleur résultat.

### F06 — Sauvegarde du CLI fragile et parseurs divergents — P2

**Emplacements :** `bin/gittoskill.mjs:59`, `bin/gittoskill.mjs:106`, `lib/parse-github-profile.ts:9`.

Le remplacement du snapshot supprime la sauvegarde avant que l'installation ait réussi. Les erreurs de renommage sont toutes ignorées ; deux exécutions simultanées partagent la même sauvegarde `.bak`. Une interruption ou une erreur de permissions peut laisser un état difficile à récupérer.

Les deux parseurs divergent aussi : l'URL `https://github.com/foo.bar` est acceptée par le CLI et rejetée par le serveur.

**Correction :** conserver une sauvegarde jusqu'à validation, distinguer l'absence du dossier des autres erreurs, prévoir restauration et verrou par profil. Partager le parseur et le contrat de sortie. Vérifier les options documentées contre la version réelle de `skills`, notamment `--scope project`.

## 3. Performances : les gains les plus utiles

### F07 — Chaque consultation régénère GitHub et Azure — P1/P2

**Emplacements :** `app/api/generate-skill/route.ts:89`, `components/gittoskill-home.tsx:151`.

La visite d'une URL de profil lance une génération côté client. Aucune couche explicite de cache des profils, des preuves ou des résultats n'est présente. Le dossier nommé `cacheRoot` dans le CLI conserve des fichiers, mais n'empêche pas une nouvelle requête de génération à chaque exécution.

**Correction :** ajouter un cache partagé persistant des résultats, avec TTL initial configurable, par exemple 12–24 heures, et un rafraîchissement explicite. Inclure le login normalisé, la version du prompt et la configuration du modèle dans l'identité du cache. Si les preuves sont mises en cache séparément, utiliser aussi leurs empreintes/version pour invalider les résultats. Ne stocker dans le cache public que des données publiques.

Fusionner les demandes simultanées pour un même profil : un cache seul n'empêche pas dix requêtes arrivant à froid de déclencher dix appels Azure. Un verrou à durée limitée doit fonctionner entre instances si l'application est répliquée.

**Bénéfice attendu :** un résultat déjà disponible évite entièrement la nouvelle génération pour cette consultation. Le gain global dépend du taux de réutilisation ; aucun pourcentage de réduction n'a été mesuré ici.

### F08 — Des dépôts sont analysés en double — P2

**Emplacement :** `app/api/generate-skill/route.ts:91`.

Les listes épinglées et populaires sont concaténées sans déduplication avant le tri et la sélection. L'utilitaire GitHub déduplique chaque liste séparément, pas leur union. La reproduction sélectionne `a, a, b, b` : seulement deux dépôts distincts pour quatre places.

**Correction :** dédupliquer par `nameWithOwner` normalisé avant le classement. Ajouter ensuite des critères de récence et de diversité de langages ; `updatedAt` existe mais n'est pas utilisé. Cela améliore à la fois le coût du contexte et la qualité de l'analyse.

### F09 — Requêtes GraphQL volumineuses et échec global sur données partielles — P2

**Emplacements :** `lib/github-client.ts:130`, `lib/github-client.ts:624`.

Chaque dépôt demande 14 manifests, 15 fichiers UI et un README, soit **jusqu'à 120 lectures de blobs pour quatre entrées**. Les textes sont tronqués après téléchargement : les limites de 2 500/5 000 caractères n'empêchent pas le transfert des fichiers complets retournés par GitHub.

Un README de profil absent peut entraîner la répétition de toute la requête de profil alors que GitHub a déjà retourné les données utilisateur. La reproduction compte deux appels dans ce scénario. Une erreur sur une partie de la requête de détails peut également faire échouer toute la génération.

**Correction :** exploiter les données partielles pour les champs optionnels et conserver des erreurs typées avec leur chemin GraphQL. Cibler les manifests selon les langages détectés, puis appliquer un repli limité. Pour les monorepos, ajouter quelques chemins pertinents plutôt qu'une exploration intégrale. Mesurer les octets et le coût GraphQL pour arbitrer entre taille des requêtes et nombre d'allers-retours. [Limites et réponses partielles GitHub](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api).

Ne pas paralléliser aveuglément le pipeline : la sélection dépend du profil et le modèle dépend des preuves. Le batch actuel est déjà un bon choix pour les demandes indépendantes.

### F10 — Aucun budget de durée ou de reprises — P1/P2

**Emplacements :** `lib/github-client.ts:112`, `lib/azure-openai.ts:151`, `bin/gittoskill.mjs:143`, `components/gittoskill-home.tsx:112`.

Aucun `AbortSignal`, délai limite explicite, budget global ou traitement dédié des erreurs 429 n'est présent. Les limites du réseau ou de l'hébergeur peuvent interrompre les opérations, mais l'application ne les maîtrise pas. L'utilisateur ne peut pas annuler le parcours depuis l'interface.

**Correction :** établir un budget total et des délais par service, propager l'annulation, limiter les reprises aux erreurs transitoires et respecter `Retry-After`/les quotas GitHub. Distinguer 400, 404, 429, 502, 503 et 504 avec des erreurs typées ; la classification actuelle dépend de mots contenus dans le message.

Pour les requêtes Azure, prévoir qu'une reprise après une coupure réseau peut avoir un coût supplémentaire si la première génération a déjà été exécutée. Ajouter des étapes visibles au client, éventuellement via SSE. Passer à une file de jobs seulement si les mesures de durée ou de concurrence le justifient.

### F11 — Markdown chargé dès l'arrivée sur la page — P2

**Emplacement :** import statique de `SkillMarkdown` dans `components/gittoskill-home.tsx:6`.

Le build local référence 8 scripts destinés aux navigateurs modernes, totalisant **572 344 octets bruts et 169 244 octets gzip estimés**, soit environ **165 Kio gzip**. Un neuvième script `nomodule` de compatibilité n'est pas compté dans ce total moderne. Le chunk contenant le parseur Markdown représente environ **38,5 Kio gzip**.

Ce sont des tailles d'artefacts compressés localement, pas une mesure de transfert en production, de LCP ou d'INP. Les polices, CSS et scripts chargés ensuite ne sont pas inclus.

**Correction :** charger le rendu Markdown avec un import dynamique lorsque les résultats existent. Monter le contenu des panneaux fermés à la demande si cela conserve une bonne expérience. Mesurer le bundle après changement : le gain exact dépend de la redistribution des chunks. [Chargement différé Next.js](https://nextjs.org/docs/app/guides/lazy-loading).

## 4. Protection du service et qualité des skills

### F12 — Génération publique sans limite applicative — P1

La route expose une génération facturable sans authentification, limitation de débit ni plafond global visible dans le code. Le lancement automatique à l'ouverture d'un profil accroît les générations involontaires. Des protections Vercel peuvent exister, mais elles ne sont pas visibles dans cette copie.

**Correction :** limiter la fréquence par utilisateur/IP avec un stockage partagé et une configuration de proxy fiable, limiter la concurrence et le budget global, puis retourner 429 avec une indication de reprise. L'authentification est une option produit ; elle n'est pas indispensable pour garder une démo publique avec des quotas. Restreindre aussi la taille du corps et des bundles.

### F13 — Le caractère public des données n'est pas vérifié partout — P1 conditionnelle

Les requêtes `repositories` filtrent `privacy: PUBLIC`, mais la lecture directe du dépôt `<login>/<login>` et les dépôts épinglés ne vérifient pas explicitement `isPrivate`. Les lectures de détails ne le vérifient pas non plus.

Avec un token ayant accès à des dépôts privés, le code ne garantit donc pas que chaque blob envoyé à Azure et retourné dans les références provient d'un dépôt public. Aucune fuite réelle n'a été reproduite ; il s'agit d'un défaut de garantie dépendant des droits du token et des données retournées.

**Correction :** demander et contrôler la visibilité avant de lire les blobs, ou restreindre le token de sorte qu'il ne puisse pas lire de contenu privé. Ne pas mettre en cache publiquement les données avant cette validation.

### F14 — Les preuves décrivent surtout les stacks, pas le code — P2

L'analyse repose sur README, dépendances et CSS. Elle ne lit pas de fichiers d'implémentation, de configuration de lint/format ni de tests du profil. Le site promet pourtant une analyse du « real code style ». Le premier manifest ou fichier CSS trouvé suffit à représenter chaque dépôt, ce qui est fragile pour les monorepos et projets multilangages.

**Correction :** ajouter un petit échantillon de code source pertinent, tests et configurations, dans un budget de contexte fixe. Structurer les résultats en traits avec preuves, chemins, commit et niveau de confiance. Vérifier les références contre les fichiers réellement récupérés ; un chemin écrit par le modèle n'est pas une preuve validée. S'abstenir sur les caractéristiques insuffisamment documentées.

Isoler les extraits GitHub comme données non fiables dans le prompt, explicitement distinctes des consignes. Un README peut contenir des instructions destinées à détourner le modèle ; les sorties installées dans un agent méritent une validation particulière. Délimiter le texte seul ne constitue pas une protection complète.

Le corps principal devrait renvoyer aux fichiers `references/` générés : ils sont actuellement présents dans le bundle mais ne sont pas reliés automatiquement depuis `SKILL.md`.

## 5. Interface, accessibilité et distribution

Ces éléments viennent après les corrections de fiabilité et les optimisations des appels externes.

- **Parcours produit incomplet :** le README promet téléchargement et commande d'installation. L'interface actuelle affiche les sections et leurs boutons de copie, sans utiliser `installCommand`, ni proposer le téléchargement. Ajouter la commande et un export du bundle avec ses références.
- **Accessibilité du formulaire :** l'input n'a pas de label ou `aria-label` ; le placeholder ne remplace pas un nom accessible. `focus:outline-none` n'est accompagné d'aucun indicateur de focus explicite. Ajouter label, message associé et focus visible.
- **Panneaux repliés :** l'animation en grille ne retire pas le contenu du DOM et ne le rend pas inerte. Des liens cachés peuvent rester dans l'ordre de tabulation. Utiliser `hidden`, `inert` ou un montage conditionnel, avec validation clavier.
- **Indication de progression :** le texte tourne toutes les 2,6 s sans refléter le backend. Les points changent toutes les 450 ms dans une région `aria-live`. Afficher des étapes réelles ; rendre l'animation décorative indépendante des annonces aux lecteurs d'écran.
- **État React :** l'effet à la ligne 160 remet à jour la section ouverte alors que `runGeneration` le fait déjà. Supprimer ce travail redondant et l'avertissement de dépendances. Centraliser le type `SkillOutput` et valider les réponses à l'exécution.
- **Routes et fichiers inutilisés :** `/[owner]/[repo]` retourne systématiquement 404 ; le parseur de dépôts et plusieurs SVG de démarrage paraissent inutilisés. Les supprimer ou expliquer clairement leur statut.
- **Distribution npm :** le même package contient le site et le CLI. `npx gittoskill` installe ainsi aussi les dépendances de production web, dont Next/React/Tailwind. Séparer un CLI léger du site, idéalement dans un workspace. Une propriété `files` doit limiter les fichiers publiés. Le dry-run a inclus le code web et les artefacts d'audit déjà présents au moment du test ; cela ne décrit pas le contenu d'un package déjà publié.
- **Documentation et hygiène :** le README annonce MIT mais aucun fichier `LICENSE` n'est présent ; `package.json` ne contient pas de champ `license`. `skills-lock.json` contient un chemin absolu vers une autre machine. Supprimer cette dépendance locale non portable ou la rendre reproductible. Documenter l'URL Azure v1 attendue et la correspondance modèle/déploiement. [Format d'endpoint Microsoft](https://learn.microsoft.com/en-us/azure/ai-services/openai/api-version-deprecation).
- **Configuration du site :** centraliser l'URL du site utilisée dans le CLI, les métadonnées, le sitemap et robots. Les pages de profils partagent actuellement les métadonnées génériques ; décider si elles doivent être indexées, puis adapter canonical et métadonnées à ce choix.
